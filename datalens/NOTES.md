## Почему ручная сборка + экспорт, а не генерация JSON

Экспорт DataLens-воркбука содержит серверный HMAC в поле `hash`,
подписанный секретом `exportDataVerificationKey`. На импорте сервер
проверяет подпись. Любой handcrafted или отредактированный JSON →
импорт падает с `workbook data hash validation failed`.

Единственный валидный путь — собрать воркбук в UI и экспортнуть.
Отсюда и формат спека: пошаговая инструкция, один раз пройти руками,
потом закоммитить результирующий `dashboard.json`.

Источник: [datalens-meta-manager / workbook-import](https://github.com/datalens-tech/datalens-meta-manager/blob/main/src/controllers/workbook-import/start-workbook-import/index.ts).

## Почему auto-import не в v1

Internal BFF DataLens (`POST /api/internal/v1/workbooks/import/`)
технически позволяет импортировать воркбук из curl, но:

- endpoint приватный, `/api/internal/v1/...` — без публичного SLA,
- контракт менялся в 2024 (hash-валидация, nullable `collectionId`),
- авторизация — session-cookie или IAM Bearer + `x-dl-tenantid`,
  надо верифицировать в devtools.

Для одиночного пользователя — ок. Для Marketplace-бандла (много
тенантов) риск «одно переименование хедера → все установки сломались»
перевешивает удобство. Подпишемся на этот путь только в Part E
и обязательно с fallback «ретраим через UI при поломке».

## Дизайн-решения

### Даты управляются только глобальным селектором

Ни в одном датасете и ни в одном чарте не зашит диапазон дат.
Период выбирается только селектором «Период» на дашборде (default:
последние 30 дней). Логика: пользователь должен свободно менять
диапазон и сравнивать разные отрезки.

Перфоманс-защита — default самого селектора; чарты не скейнят всю
историю на первом рендере.

### WoW-дельта в KPI — не вошла в v1

У DataLens Индикатор нет нативного переключателя «Сравнение с
предыдущим периодом». Пути реализации:

- (а) дубликат чарта со сдвинутым per-chart фильтром, два индикатора
  рядом;
- (б) calc-field-дельта в датасете:
  ```
  SUM(IF([Дата] BETWEEN TODAY()-60 AND TODAY()-30, [Доход], 0))
  ```
  но тогда глобальный «Период» на эти KPI работать перестанет.

Оба варианта — костыль, фича не стоит усложнения. Откладываем
до v2 по реальному запросу.

### Top-N через `RANK_DENSE`, а не через «Количество элементов»

В DataLens нет универсального UI-контрола «показать top-N категорий»
(в одних визуализациях есть ограничитель, в других — нет). Единый
способ, работающий везде:

```
Ранг источника = RANK_DENSE(SUM([Число конверсий]) AMONG [Название источника атрибуции])
```

Потом в чарте фильтр `Ранг источника <= N`. Ранг пересчитывается
в контексте чарта — с учётом всех глобальных селекторов, так что
«top-N в выбранном пользователем срезе» работает автоматически.

### Почему `ch_time_series` — не по моделям

Кросс-модельный инвариант: сумма кредитов любой модели за сутки =
числу конверсий (тест: `test_all_models_total_equals_conversion_count`).
Четыре линии «по моделям» в time series просто накладываются друг
на друга — бесполезный чарт.

Вместо этого `ch_time_series` показывает **топ-источники под
выбранной моделью** (цвет = источник, модель — из селектора).
Переключение модели перерисовывает график — это и есть видимая
разница между моделями во времени.

### Имена источников — готовая колонка в view, словари в dicts/

Префиксный CASE в датасете больше не используется.  Имена приходят
готовой строкой в колонке `source_name` у представления
`v_attribution_results` (см. `sql/01_schema.sql`).

Что меняется:

- `SearchEngineID` в `02_prepare_visits.sql` заменён на
  `SearchEngineRootID` — коллапсит вариации «Яндекс.Поиск /
  Картинки / Карты» в один бакет «Яндекс».  SourceCode вида
  `2_<root>` теперь имеет смысл «поиск такой-то системы», а не
  «конкретный поддомен поиска».
- Пять словарей `dict_*` в ClickHouse заполняются из CSV в
  папке `dicts/` (грузит `handler.py` при каждом прогоне).  Формат
  CSV — `id,name_ru`, см. `dicts/README.md`.
- View `v_attribution_results` JOIN'ит словари и склеивает префикс
  типа источника (hardcoded, т.к. их всего 12 и они стабильны)
  с именем из словаря.
- Fallback при отсутствующем id: `"Поиск: код 1234"` — данные не
  теряются, подпись становится читаемой после дополнения CSV.

DataLens-датасет `ds_attribution` теперь смотрит на view, а не на
таблицу — см. BUILD_SPEC §3.  Calc-поля «Название источника» больше
не нужно.

## Что пробовали и не взлетело

### Sankey через Gravity UI Charts

- **Путь**: Чарт в Editor → шаблон «График (Gravity UI Charts)» →
  `module.exports = {series: {data: [{type: 'sankey', ...}]}}`.
- **Результат**: `bar-x` с теми же данными рисуется, `sankey` —
  пустой Preview, пустой Console. Тип не поддерживается в текущей
  версии Gravity UI Charts, которая едет с DataLens.
- **Вывод**: путь мёртвый до появления нативного sankey. Fallback
  через Advanced-чарт (HTML+SVG) с инлайн d3-sankey-layout возможен,
  но требует ~50 строк layout-кода руками (require внешних модулей
  в редакторе нет) — не стоит этого в v1.

**Замена**: вместо Sankey — тепловая карта переходов (`ch_transitions_heatmap`
в BUILD_SPEC §7), датасет `ds_transitions` над таблицей
`source_transitions`, заполняемой в `05_attribution_models.sql`.
Показывает те же данные prev→next, но в виде матрицы, а не потоков;
отрисовывается штатным heatmap-виджетом без Editor-костылей.  Если
однажды в Gravity UI Charts завезут нативный sankey — встанет на
тот же датасет без миграции данных.

## v2 — на сортировку

### Нативный Sankey (когда появится в Gravity UI Charts)

Данные для сanky уже лежат в `source_transitions` (prev→next,
count) — это тот же контракт `{nodes, links}`, который ожидает
d3-sankey.  Как только в Gravity UI Charts завезут `type: 'sankey'`,
тепловая карта `ch_transitions_heatmap` меняется на Sankey без
переработки пайплайна — только правка Editor-шаблона.

### WoW-дельта в KPI

По запросу — один из двух путей выше (дубликат чарта vs calc-field).

### Когортный анализ

Когорты по дате первого касания (каждого пользователя), разрез по
retention / конверсии. Требует:
- выход за `attribution_results` в `visits_combined` / `visits_raw`,
- идентификатора пользователя (`CounterUserIDHash`),
- дополнительного датасета с `first_touch_date` per user.

### Кампании Яндекс Директа

Добавить `ClickID` / `utm_campaign` к `source_code`, чтобы сравнивать
кампании, а не только каналы. Требует пересборки `visits_prepared`
с новыми полями и адаптации `03_combine_visits.sql` / `05_attribution_models.sql`.

### ROAS-калькулятор

Требует поля «стоимость рекламы» — в Метрике его нет, нужен отдельный
источник (Директ API / ручной импорт затрат). Отдельная фича уровня v3.
